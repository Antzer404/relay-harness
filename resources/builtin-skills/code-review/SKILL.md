# 代码评审

目标是找出真正影响正确性、安全性或维护性的问题，而不是复述 diff。

## 1. 确定评审范围

- 用户指定了分支、提交或文件时按指定范围；否则先看 `git status`，再审 `git diff`（含暂存区）。
- 改动跨多个关注点时按模块逐个评审，不要漏掉新增文件。
- 不要只读 diff：打开改动所在文件的上下文，确认调用方、数据形状和既有约定。

## 2. 检查清单

- 正确性：边界值、空值、错误分支、状态机、并发/竞态、异步取消。
- 安全：注入、路径穿越、命令拼接、密钥或日志泄露、缺失的权限校验。
- 兼容性：函数签名、序列化格式、配置字段、旧数据与迁移。
- 性能：热路径上的重复 IO、无界循环、未索引查询；先有证据再下结论。
- 测试：行为变化是否有测试覆盖；能跑相关测试就实际跑一遍并记录结果。
- 一致性：命名、目录、错误处理方式是否遵循仓库已有习惯。

## 3. 输出格式

先给结论：**可合并** / **建议修改** / **有阻塞问题**。

然后按严重程度列出：

1. `[阻塞] path/file.ts:120` — 问题是什么；会触发什么场景；最小修复建议。
2. `[建议] path/file.ts:88` — 可以更好，但不影响正确性。
3. `[疑问]` — 需要作者确认的假设或意图。

最后补充：运行了哪些测试/命令、还有哪些部分没有验证。

## 约束

- 每条结论都要能指到具体行；推测必须标注"推测"。
- 不为凑数提纯风格问题；不重写整个文件，给最小 diff 或伪代码。
- 回复语言跟随用户。
